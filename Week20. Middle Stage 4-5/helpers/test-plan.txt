Words used in these files
-------------------------

client (ApiClient)
   The one class that sends HTTP requests. Every answer comes back in the same shape:
   status, ok, body, durationMs, attempts.

interceptor
   A small function every request passes through: auth (adds the token), retry (tries
   again when the server is briefly down), logging (writes each request to the report).

service
   A class for one resource, with one method per endpoint - for example
   petstore.pets.get(7) sends GET /pet/7.

fixture
   Something Playwright prepares before a test and cleans up after it - for example
   "pet", a new pet that exists on the server during the test.

environment
   A named set of settings (test user, retries, timeout). Chosen with TEST_ENV=dev or
   TEST_ENV=staging; the code stays the same.

edge case
   An input or situation at the border of what an endpoint is made for: a missing field,
   a value just past a limit, a list with one bad item, a job that is not finished.

negative test
   A test that sends something wrong on purpose and checks the API refuses it correctly.

boundary value analysis (BVA)
   Testing the value just below a limit, on it, and just above it.

bulk request
   One request with a list of items (several books, several users).

partial failure
   A bulk request where some items work and some do not.

error consistency
   Every endpoint of an API answers errors in the same shape, so a client can read them
   with one piece of code.

asynchronous operation
   The server answers at once ("accepted", 202) and does the work later.

polling
   Asking again and again, with a pause, until the work is done - always with a limit.

webhook
   The opposite of polling: the server calls the client back when the work is done.

idempotent
   Doing it twice leaves the same state as doing it once. PUT and DELETE should be;
   POST does not have to be.

multipart (multipart/form-data)
   A request body made of parts - fields and files - like a web form with a file.

mock, simulation
   A small server of our own that plays a real API. Here: the job server in mocks/.

flaky test
   A test that sometimes passes and sometimes fails without any change in the code.

deterministic data
   Test data that is the same, or made the same way, every run - nothing depends on
   what another test or another person left on the server.

seeded data
   Test data that is ready before the test starts: a new account, a new pet.

leaked data
   An account, pet, user or order that the cleanup could not delete. Shown in the report.

test.fail
   A Playwright mark: "this test is expected to fail", because the API does not do what
   it should. If it ever passes, the run turns red.

known deviation
   A place where an API does not do what it should, kept visible with test.fail.

precondition
   A step that only prepares a test. Its check says "precondition:".

infrastructure failure
   A failure caused by a server or the network (for example 502 Bad Gateway), not by the
   test and not by the settings of the run.

@ui, @slow
   Tags in a test's options. @ui needs a browser; @slow waits a long time (1 minute).

Basic auth
   A login sent as "user name:password" in a header. DemoQA accepts it for deleting an
   account, which the cleanup uses when the token way does not work.

Practice task 1. "Implement 5 categories of negative tests for one endpoint"
----------------------------------------------------------------------------

Where:    tests/bookstore/addBooksNegative.spec.ts - 15 tests on one endpoint,
          POST /BookStore/v1/Books
Covers:   1 missing fields, 2 invalid format, 3 unauthorized access, 4 business rule
          violations, 5 duplicate data
Checks:   the status, the error body { code, message }, and (in the 7 passing tests
          that send books) that the collection did not change
Found:    7 deviations (assertion-notes.txt, 13-19): three server crashes (500), a format
          error answered as a login error, an HTML error page, and two rules that work
          only for a one-book request


Practice task 2. "Apply boundary value analysis to at least 3 parameters"
-------------------------------------------------------------------------

Done for 7 parameters on three APIs - on each limit, and below / above it wherever the
parameter has such a value:

   GET /products limit          DummyJSON   tests/dummyjson/boundaries.spec.ts
   GET /products skip           DummyJSON   same file
   GET /test delay              DummyJSON   same file
   POST /auth/login             DummyJSON   same file
     expiresInMins
   password length              DemoQA      tests/bookstore/accountBoundaries.spec.ts
   user name + password length  DemoQA      same file
   shipDate (a date-time)       PetStore    tests/petstore/orderDates.spec.ts

How:      limits that depend on data are read from the API; "accepted" is checked by its
          effect (the number of products, the token's lifetime, the date as stored)
Found:    a token "for 0 minutes" lives 30 days; a too-long lifetime gets 500, not 400;
          DemoQA creates accounts of 85+ characters that can never log in; PetStore
          turns dates that do not exist into other dates, and crashes on the year 10000
          (assertion-notes.txt, 6, 7, 20, 34-36)


Practice task 3. "Test a bulk/batch operation with partial failures"
--------------------------------------------------------------------

Where:    tests/bookstore/bulkAdd.spec.ts (6), tests/petstore/bulkUsers.spec.ts (2)
Rule:     the answer must match what really happened - an error and nothing changed, or
          success and the answer lists exactly what was done. Every item is checked on
          the server.
Covers:   the bad item first, in the middle, last; items that existed before; a list of
          bad items only; a wrong field type; an empty item
Found:    DemoQA's answer lists books it did not add; PetStore answers "error" after
          creating half of the users (assertion-notes.txt, 11, 12, 28)


Practice task 4. "Validate error response consistency across 3+ endpoints"
--------------------------------------------------------------------------

Where:    tests/dummyjson/errorConsistency.spec.ts (7),
          tests/bookstore/errorConsistency.spec.ts (12),
          tests/petstore/errorConsistency.spec.ts (10)
How:      one shared error check per API (assertions/<api>/errorAssertions.ts), used on
          every endpoint in a table; plus "the same error has the same code"
Covers:   29 checks: 7 DummyJSON, 12 DemoQA, 10 PetStore - accounts, books, products,
          users, posts, pets, orders, login
Found:    an HTML page, empty bodies, 200 for a failed login, one code for several errors,
          two codes for "not found" (assertion-notes.txt, 8, 21-27)


Practice task 5. "Write a test for an async operation with polling"
-------------------------------------------------------------------

Where:    tests/dummyjson/tokenExpiry.spec.ts (1, real server, @slow),
          tests/jobs/jobPolling.spec.ts (6, local simulation)
Real:     a 1-minute token works, then is refused with "Token Expired!" - found by
          polling every 5 s with a limit of 2 minutes
Simulated: a job is accepted (202), polled until done or failed, with a limit; the last
          poll is at the limit itself; an unknown job is 404; the webhook brings the same
          result as polling
Why a simulation: none of the public APIs here has background jobs. The job server is
          called a simulation in the code and in these documents.

Expected demonstration - where it shows
---------------------------------------

"Can independently identify negative/edge-case scenarios"
   edge-case-strategy.txt, part 1 (four questions for every endpoint) - and the 28 new
   deviations, each found by trying the API live first (assertion-notes.txt).

"Apply boundary analysis systematically"
   The same rule for 7 parameters: below / on / above, limits from data, "accepted"
   checked by its effect (edge-case-strategy.txt, part 3).

"Validate both individual endpoint correctness and cross-endpoint consistency"
   Individual: addBooksNegative, boundaries, uploadImage - one endpoint, many cases.
   Cross-endpoint: errorConsistency in three APIs - one check on many endpoints.

"Build stable, deterministic tests that don't depend on timing or order"
   Own data per test, cleanup that always runs, no sleep, every wait with an interval
   and a limit, no upper time limits in checks (two named exceptions from week 18,
   README.txt part 12), tests run in parallel and in any order
   (edge-case-strategy.txt, part 8). Proof: practice task 6.

What changed compared to the week 19 code
-----------------------------------------

- PetStore as a third API: services (pets, users, orders), models, factory, fixture with
  cleanup, error check.
- A local job server (mocks/), its service and fixture.
- ApiClient: one new option, multipart. The retry interceptor now also retries DELETE on
  502/503/504.
- The DemoQA cleanup: deletes with the password when the token way fails; the note in
  the report is "leaked data" for every API.
- New service methods: AuthService.login with a token lifetime, BookStoreService
  addBooksRaw and getBook, AccountService.deleteWithPassword, StoreService.createOrder.
- Two DemoQA rules moved from businessRules.spec.ts to addBooksNegative.spec.ts (same
  titles). Week 19's "all or nothing" test (gap S8) moved from collection.spec.ts to
  bulkAdd.spec.ts and was widened to accept partial success.
