Code review of Middle Stage 5
=============================

What this file is for: the record of every code review made during Middle Stage 5 - what
was found, what was fixed, what was left on purpose and why. One part per step, written
before the commit of that step. (The reviews of Middle Stage 4 are in code-review.txt.)


In short
--------

- Stage 5 is done in a branch (week20-middle-stage-5) with a pull request, so that the
  "smoke on pull request" trigger really runs. Every step is reviewed before its commit.
- Step 1 (tags, CI suites, secrets): 8 findings - 7 fixed, 1 left on purpose.
- Step 2 (reports, job order, shards, numbers): 9 findings - 8 fixed, 1 left on purpose.
- The browser test in a ready-made image: 6 findings - all fixed.
- Step 3 (the data-driven password table): 10 findings - 9 fixed, 1 left on purpose.

1. How a review is done here
----------------------------

The same way as in Stage 4 (code-review.txt, part 1): an AI reviewer reads the staged
changes only - it does not change files and does not run the tests. Every finding is
checked in the code by hand before a decision, and each decision has a reason.

How each finding is written:
   Found:     what the reviewer saw
   Example:   when it would hurt
   Decision:  fixed / not changed, and why


2. Step 1 - tags, CI suites and secrets (26 October 2026)
---------------------------------------------------------

What the step changed: test tags (config/tags.ts) on every test; npm scripts for the
suites; the CI workflow picks the suite from what started it (pull request - smoke, push
to main - regression, night - full, by hand - any); the DummyJSON passwords moved out of
the code into environment variables (.env locally, GitHub Secrets in CI); different
settings for a local run and a CI run (playwright.config.ts).

S1-1. A missing password stopped every test
   Found:     the password was checked when the config was loaded, so without the
              DummyJSON password not a single test could start - also the PetStore, DemoQA
              and job server tests, which do not need it.
   Example:   a local run of tests/petstore on a computer without the password fails.
   Decision:  fixed. The password is read only when a test logs in to DummyJSON. Without
              it, every DummyJSON test fails with the same clear message
              ("DUMMYJSON_PASSWORD_DEV is not set. Locally: copy .env.example ..."), and
              the other APIs still run. Checked: without the password, 2 PetStore tests
              passed and the DummyJSON test failed with that message.

S1-2. A test without a tag would silently miss the regression suite
   Found:     regression is "--grep @regression". A new test that nobody tags runs only in
              the full suite at night.
   Example:   a new spec file is added without tags; it passes the review, but the push
              to main never runs it.
   Decision:  fixed, but the tags stay. The task asks for tagging smoke vs regression, so
              the tags are explicit. A new CI step "Every test is in a suite" lists the
              tests that have neither @regression nor @slow and fails the job if there is
              one. Checked: a test file without tags was found by that command; with the
              real tests the list is empty.

S1-3. Traces were switched off for every test in CI
   Found:     to keep the DummyJSON login password out of the downloadable report, CI
              had no trace at all - the main tool for a failed browser test was gone.
   Decision:  partly fixed. API tests stay without a trace in CI: their api-log already
              shows every request, and a trace would contain the password. The UI test
              turns the trace back on for itself (profileUi.spec.ts) - it does not log in
              to DummyJSON, and its DemoQA account is new and closed after the test.

S1-4. The DummyJSON user could be changed, its password not
   Found:     DUMMYJSON_USERNAME could still override the user, but the password belongs
              to the environment's own user.
   Example:   another user with the password of "emilys" - every DummyJSON login fails
              with "Invalid credentials".
   Decision:  fixed. The user is fixed per environment and cannot be overridden; the
              override was removed from the code, .env.example and README.txt.

S1-5. Every job got both passwords
   Found:     both matrix legs and the UI job received both secrets.
   Decision:  fixed (least privilege). The dev leg gets only DUMMYJSON_PASSWORD_DEV, the
              staging leg only DUMMYJSON_PASSWORD_STAGING, the UI job none - it uses
              DemoQA only, and the password is no longer needed to load the config.

S1-6. The smoke suite broke its own rule
   Found:     the rule says "one or two happy paths per API", but DummyJSON had 5 of the
              9 smoke tests.
   Decision:  fixed. Smoke now has 6 tests: DummyJSON 2 (the environment's user logs in;
              a protected endpoint with a valid token), DemoQA 1 (the reader journey),
              PetStore 2 (a pet's life; an upload), job server 1 (202, then done).
              About 6 seconds without DemoQA delays.
   Later:     the first CI run on the pull request showed that the reader journey (~12
              DemoQA requests) does not fit into 60 s when DemoQA is slow. The DemoQA smoke
              test is now "the minimum: 8 characters are accepted" (3 requests), and the
              rule says "as few requests as possible"
              (reports/2026-10-26-ci-smoke-demoqa-slow.txt).

S1-7. CI runs could cancel each other
   Found:     the concurrency group was "event + branch" with cancel-in-progress for all.
   Example:   two quick merges to main - the regression run of the first one is
              cancelled and that commit never gets a result; a run by hand with suite
              "smoke" cancels a running "full".
   Decision:  fixed. Only a pull request cancels its own older run (a newer push replaces
              it). Runs on main and night runs are never cancelled. A run by hand has the
              suite in its group, so different suites do not cancel each other.

S1-8. CI=false would count as CI
   Found:     "isCI = !!process.env.CI" treats any value as CI, also "false".
   Decision:  not changed. GitHub Actions sets CI=true, and Playwright's own templates use
              exactly this check. Nobody in this project sets CI=false; a run "like CI" is
              started with CI=1.

How it was checked after the fixes
   - tsc clean; the workflow file parsed without errors.
   - Suites: smoke 6, regression 153, slow 1, ui 1 - 154 in total.
   - Smoke in CI mode: dev 6 of 6, staging 6 of 6. The UI test in CI mode: passed.
   - The whole regression suite in dev in CI mode, after the fixes: 152 of 152 as
     expected, 0 flaky, no leaked data (137 s). (The UI test is the 153rd - it runs in
     its own job.)


3. Step 2 - reports, job order, shards and numbers (26 October 2026)
--------------------------------------------------------------------

What the step changed, in plain words: a CI run is now four groups of jobs in a row -
"checks" (is the code fine, which tests to run), "test" (the tests, the dev part split in
two halves that run at the same time), "ui-test", and "report" (glues the halves together
and makes the HTML report, the Allure report with charts of earlier runs, a JSON file, and
a small table of numbers on the run's Summary page).

Most findings were about one thing: what the "report" job does when something went wrong
earlier. That is exactly when a report is needed most, so it had to be solid.

S2-1. One missing half meant no report at all
   Found:     if one test job stopped early (a timeout, a broken install), it left no raw
              results. The report job then failed at its first step, and everything after
              it - the Allure report, the numbers, the downloads - was skipped.
   Decision:  fixed. The report job first counts how many parts arrived. It builds the
              reports from what is there, and the steps after that run even if one step
              failed. Downloading a missing part no longer stops the job.

S2-2. A missing half looked like a good run
   Found:     with one half missing, the table would show only the tests of the other
              half - for example 40 tests, 0 failed, 100% - and look perfectly fine.
   Decision:  fixed. The report job knows how many parts were planned (from the plan the
              "checks" job made). If fewer arrived, the Summary starts with "WARNING: only
              1 of 3 parts of this run finished - the numbers below are incomplete."
   Seen live: in run #15 the browser test job failed before it started, and the dev
              summary said "WARNING: only 2 of 3 parts of this run finished" above a
              table that would otherwise have looked all green (152 tests, 100%).
              Screenshot: screenshots/ci-regression-run-15-summary-warning.png

S2-3. A cancelled run still made reports
   Found:     when a newer push to the pull request cancels an older run, the report jobs
              of the old run still started and could even save a half-finished run into
              the Allure history.
   Decision:  fixed. The report job runs after failures, but not after a cancelled run.

S2-4. "1 min 60 s"
   Found:     minutes and seconds were rounded separately, so 119.6 seconds became
              "1 min 60 s".
   Decision:  fixed. The total is rounded first, then split: "2 min 0 s".

S2-5. A flaky test lowered the pass rate
   Found:     a test that failed once and passed on the retry ended green, but the pass
              rate still counted it as not passed - a green run showed 95%.
   Decision:  fixed. The pass rate is now "the share of tests that ended green"; flaky
              tests have their own column, so they are still visible. If every test was
              skipped, the rate shows "n/a" instead of 0%.

S2-6. A re-run counted twice in the history
   Found:     if the report job was started again ("Re-run failed jobs"), the same run
              would be added to the Allure history a second time.
   Decision:  fixed. Only the first attempt of a run adds its point to the history.

S2-7. The staging report waits for the browser test
   Found:     the report job for staging also waits for the browser test, which only
              belongs to dev - up to a minute or two longer. And the list of environments
              in the report job is written by hand, next to the plan.
   Decision:  not changed. Splitting the report job in two would make the workflow
              harder to read for a minute of waiting, and the run is not finished before
              the browser test anyway. We have two environments; if a third one comes, the
              list is one line to change.

S2-8. Incomplete runs went into the trend
   Found:     a run with a missing part was saved into the history like a normal run, so
              the pass-rate trend could drop for reasons that are not test failures.
   Decision:  fixed. A run adds a point to the history only when all its parts arrived.
              (The history file itself is tiny; GitHub removes cache entries nobody used
              for 7 days.)

S2-9. The suite name came from two places
   Found:     the report job read the suite name from the "checks" job and also had it
              from the workflow - two sources that could one day disagree.
   Decision:  fixed. The report job uses the one from the workflow, like the other jobs.

How it was checked
   - Locally, the CI way: smoke in two halves, plus the browser test, glued into one
     report (7 tests); a test.fail test counted as a "known deviation", not a failure;
     a missing results file and a missing part produce the warning instead of a crash.
   - Allure: the results of both halves are kept; the history grows by one line per
     report, and does not grow when appending is switched off.
   - tsc clean, the workflow file parsed without errors.
   - The real check is the first CI run of this step: every job group and every download
     on one page.


4. The browser test in a ready-made image (26 October 2026)
-----------------------------------------------------------

What changed, in plain words: the browser test job now runs inside Playwright's own Docker
image, where the browser is already installed. Installing it every time took 11 of the
job's 12 minutes (ci-improvements.txt, part 2).

The reviewer first checked the parts that usually break in such a setup - file
permissions inside the container, where the browser lives, the CI variables, the paths of
the downloads - and found them fine. Then six smaller points:

S3-1. The version check could be fooled
   Found:     to keep the image and Playwright on the same version, a check searched the
              whole workflow file for the version text. A comment with that text would
              have been enough to pass, even with a wrong image.
   Decision:  fixed by S3-2 - the check is no longer needed.

S3-2. The version did not need to be written by hand at all
   Found:     the image version was typed into the workflow, and a check compared it with
              the project. GitHub can build the image name from what an earlier job found.
   Decision:  fixed. The "checks" job reads the Playwright version of the project, and the
              browser job takes the image of exactly that version. An update of Playwright
              now needs no change in the workflow.

S3-3. The check looked at the wrong package
   Found:     the version was read from @playwright/test, but the browsers belong to
              playwright-core - the package that really runs the tests.
   Decision:  fixed. The version now comes from playwright-core.

S3-4. Node.js was installed again inside the image
   Found:     the image already has Node.js, but the job still downloaded another one, and
              its npm cache could not be shared with the other jobs anyway.
   Decision:  fixed. The browser job uses the Node.js of the image.

S3-5. A wrong number in ci-improvements.txt
   Found:     the document said 4 tests talk to DemoQA at the same moment. A GitHub machine
              has 4 processor cores, and Playwright uses half of them - so it is 2 tests at
              once per machine.
   Decision:  fixed: "4 instead of 2" when DemoQA is split over two machines.

S3-6. A wrong reason in ci-improvements.txt
   Found:     the document said "more machines do not help, the order is still
              alphabetical". They would help a little: with 4 machines the DemoQA tests
              spread over two of them.
   Decision:  fixed. The real downside is written instead: more DemoQA tests at the same
              moment, and more machine minutes.

How it was checked
   - The workflow file parsed without errors; the line that writes the version gives
     "playwright=1.63.0" here, the version in package-lock.json.
   - The real check was the next regression run (#15) - and it found a problem no review
     had seen: inside a container, a working folder with spaces in its name does not
     work ("No such container: Middle"). The browser job now starts in the repository
     root and goes into the week folder itself (ci-improvements.txt, part 2).


5. Step 3 - the data-driven password table (26 October 2026)
------------------------------------------------------------

What the step added, in plain words: one test for the password rules of a new DemoQA account,
driven by a table of 12 rows - 11 rules DemoQA follows and 1 it breaks (a dot is not taken as
a special character, deviation 37 in assertion-notes.txt). Each row is one rule in plain
words and becomes its own test, named after the rule.

S4-1. A server outage looked like the expected failure
   Found:     the row DemoQA breaks is expected to fail - and any failure would do, also a
              502 from a server that is down.
   Decision:  fixed. A 502, 503 or 504 now skips the row with the reason "infrastructure"
              (the same as in the bulk tests), for every row of the table. A timeout with no
              answer at all can still hide in the expected failure - the same known limit
              as in Stage 4 (assertion-notes.txt, part 8).

S4-2. Two passwords that look the same
   Found:     the Cyrillic row "Тest!123" looks exactly like "Test!123" in the report.
              Nobody could see why one is refused and the other accepted.
   Decision:  fixed. The row now says it in words: 'a Cyrillic capital "Т" (U+0422)
              instead of the Latin "T"', and the code writes the letter as Т.

S4-3. The expected failure was not declared as test.fail
   Found:     the table picked test or test.fail through a variable - against the mentor's
              rule that a known deviation is declared as test.fail('title', ...).
   Decision:  fixed. The table is split: the rules DemoQA follows (declared with test) and
              the rule it breaks (declared with test.fail, with the comment above it).

S4-4. DemoQA's error texts were copied twice
   Found:     the long "Passwords must have ..." message was written in this spec and again
              in errorConsistency.spec.ts.
   Decision:  fixed. Both texts are in test-data/bookstore/constants.ts, used by both.

S4-5. Some rows repeat older tests
   Found:     7 and 8 characters, a weak password and a missing password are also checked
              in older specs (accountBoundaries, businessRules, errorConsistency).
   Decision:  not changed. The older tests are the evidence of Stages 3 and 4 and stay as
              they are; the table is the complete rule in one place, as the Stage 5 task
              asks. The cost is a few short requests (a refused password creates nothing).

S4-6. A new kind of answer would be checked the wrong way
   Found:     everything that was not "missing" was checked as "too weak".
   Decision:  fixed. The expected answers are a lookup table: a new kind of refusal without
              its own entry does not compile.

S4-7. "The list" that was never shown
   Found:     a row said "another special character from the list", but the list was not in
              the table or in the comment.
   Decision:  fixed. The comment above the table names the 8 characters DemoQA accepts
              (! @ # $ % ^ & *), and the row says "another of the 8 special characters".

S4-8. "Accepted" did not prove the account works
   Found:     an accepted row checked only "201 created". In Stage 4 we saw DemoQA create
              accounts that can never log in (deviation 20).
   Decision:  fixed. "Accepted" now means: created AND able to log in with this password.

S4-9. The numbers in the documents disagree
   Found:     assertion-notes.txt counts 166 tests and 37 deviations; test-plan.txt still
              shows the Stage 4 numbers (154 and 36).
   Decision:  test-plan.txt is rewritten for Stage 5 in the last step, with all the
              numbers; until then it describes Stage 4.

S4-10. Deviation 37 was in its own section
   Found:     it is a DemoQA deviation, but it stood in a new section after PetStore.
   Decision:  fixed. It is in the DemoQA section now (9-23, 37).

How it was checked
   - Live first: 14 passwords and 31 special characters sent to DemoQA, every created
     account deleted right away.
   - The table 3 times in a row, retries off: 36 of 36 as expected, no leaked data; the dot
     row failed every time at "the account is created" (expected 201, received 400).
   - errorConsistency.spec.ts with the shared texts: 12 of 12. tsc clean.
