AI-assisted test ideas
======================

Stage 3 evidence: a reusable prompt for getting test ideas from an AI, and
what we did with the answer.


In short
--------

- One prompt with four parts: context, instruction, limits, format.
- Only the first part changes for a new API; the rest is reused as it is.
- 4 of the AI's ideas are recorded below: 2 accepted (1 of them changed and
  written as a test), 2 rejected. Nothing was copied in without checking it.


The prompt
----------

Used to get new test ideas for a resource before writing tests. Change the
context (API name, endpoints, existing tests) for each new resource; keep
the rest.

    Context: I'm testing the Restful Booker API (POST/GET/PUT/DELETE /booking,
    POST /auth) as a Junior QA learner. Existing tests cover: create+retrieve,
    update+verify, delete+verify absence, missing auth, wrong Content-Type.

    Instruction: suggest 5 additional test-case ideas for this resource that
    are NOT already covered above, at a Junior difficulty level (no
    boundary-value analysis, no bulk operations, no async flows).

    Constraints: each idea must map to a real endpoint this API actually
    exposes. Do not invent endpoints or fields that aren't in the Restful
    Booker docs.

    Format: a numbered list, one line per idea, no code.


Why the prompt has these four parts
-----------------------------------

Context       tells the AI what already exists, so it does not repeat it
Instruction   asks for a fixed number of ideas, at the right level
Constraints   stops the AI from inventing endpoints that do not exist
Format        a short list is quick to review


What we did with the answer
---------------------------

1. "Test GET /booking/{id} with a non-numeric id"
   Decision:  accepted
   Why:       a real and cheap edge case. Not written as a test yet.

2. "Test rate limiting with 429"
   Decision:  rejected
   Why:       Restful Booker has no documented rate limit. Checking a status
              for behaviour the API does not have would be guessing, not
              testing.

3. "Test PATCH /booking/{id} for a partial update"
   Decision:  accepted, changed, and written as a test
              (tests/bookingEdgeCases.spec.ts)
   Why:       the AI only said "test PATCH". We added a check that the fields
              NOT sent stayed the same - that is what makes PATCH different
              from the PUT test we already had.

4. "Test booking creation with an XML body"
   Decision:  rejected
   Why:       out of scope - Stage 1-3 uses only JSON.


Lesson
------

Every AI idea was read and checked against the real API documentation. It
was kept only if it was both real and useful.
