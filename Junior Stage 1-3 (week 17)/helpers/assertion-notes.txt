Assertion choices and known deviations
======================================

Stage 2 evidence: why each kind of check was chosen, and the 2 places where
Restful Booker does not do what the task asks.


In short
--------

- Every check follows the task text, word for word.
- 2 tests are marked test.fail, because Restful Booker answers differently:
  201 expected but 200 received, and 401 expected but 403 received.
- The checks compare the answer with the data the test sent, not with fixed
  numbers, and one schema check proves the whole answer has the right shape.

The main rule
-------------

Every check follows the exact words of the Junior Stage 1-3 task. It is NOT
changed to match what Restful Booker really returns.

When the API behaves differently:
- the test still checks what the task says,
- a one-line comment above the test names the problem,
- the problem is listed below.

So a failed check can mean two things: "the code is broken" or "the API
behaves differently from the task". Telling them apart is part of the
exercise.


Known deviations - 2 tests that fail on purpose
-----------------------------------------------

1. Creating a booking
   Test:    bookingCrud.spec.ts
            "POST /booking with valid data returns 201 and the new booking id"
   Task:    201 Created
   API:     200 OK

2. Writing without a token
   Test:    bookingAuth.spec.ts
            "PUT /booking/{id} without a token returns 401"
   Task:    401 Unauthorized
   API:     403 Forbidden

How they are marked
   Both tests are declared as test.fail('title', ...) instead of
   test('title', ...), so the mark is on the title line, not hidden inside
   the test.

What test.fail does
   - the test fails, as expected   -> Playwright shows it as passed,
   - the test suddenly passes      -> Playwright shows it as failed.

   The check itself is not changed: it still asks for 201 and 401. The second
   case would mean Restful Booker has changed - so the run turns red exactly
   when this list needs a review.


Other Playwright marks we considered
------------------------------------

test.skip - not used
   A skipped test does not run at all, so the real API behaviour would be
   hidden. We want these two tests to call the real API on every run.

test.fixme - not used
   It fits another case: a task that cannot be tried at all, because the API
   has no such endpoint. That does not happen in Stage 1-3.

test.only - not committed, ever
   Only for running one test locally while debugging. Committed, it would
   silently switch off all other tests for everyone, CI included.


Why each kind of check was chosen
---------------------------------

One exact status (toBe), not a range
   The only exception is the wrong Content-Type test: the task says "observe"
   there, so it only checks that the server answered at all.

Answer compared with what was sent
   Body fields are compared with the data the test itself sent (made by
   buildBooking()), never with a fixed value. This proves the answer really
   reflects the request.

Schema check (zod)
   Used in the GET and PUT tests, written as
   expect(() => bookingSchema.parse(body)).not.toThrow().
   - Checking 2-3 fields by hand proves only those fields.
   - The schema proves the whole answer has the right fields and types.
   - When it fails, the error lists exactly which fields are wrong.

Array.every() for lists (bookingCollection.spec.ts)
   The list promises that EVERY item has a numeric booking id. Checking only
   the first item cannot prove that.

Optional chaining (?.) where a value can be missing
   - the first item of an empty list: body[0]?.bookingid
   - a nested field that does not exist: body?.bookingdates?.extra?.value
   Without ?. the test would crash with an error. With it we get "undefined"
   and check that with toBeUndefined().

Strict equality
   toBe already compares strictly, and on failure it shows the Expected and
   Received values. Plain === is used only inside the every() and some()
   callbacks. We avoid expect(a === b).toBe(true): on failure it only says
   "expected true, received false". Loose == is never used.

toBeLessThan only for response time
   The 5-second limit is generous on purpose: it is a sanity check, not a
   performance limit.


Why tests create and delete their own data
------------------------------------------

Every CRUD and auth test creates its own booking - before the test
(beforeEach) or inside it - and deletes it after the test (afterEach) or at
the end of the test.

So any test can run alone or in any order, and never depends on data left by
another test. This is the Stage 3 isolation requirement;
bookingIsolation.spec.ts shows it on its own.


Notes on single tests
---------------------

The test files keep only one-line comments. The longer explanations are here.

DELETE answers 201 (bookingCrud.spec.ts)
   Restful Booker answers a successful DELETE with 201 Created; 200 or 204
   would be more usual. The test checks 201, because that is what this API
   really does, and then a GET proves the booking is gone (404).

Cleanup in "Booking creation" (bookingCrud.spec.ts)
   These tests create the booking inside the test, so beforeEach cannot do it
   for them. Each test saves the new id, and afterEach deletes it. This works
   for the test.fail POST test too: the id is saved before the failing check.

Wrong Content-Type (bookingCrud.spec.ts)
   The task says "observe the behaviour", not "expect status X". So the test
   prints the status and body and only checks that the server answered.
   Restful Booker answers 500 Internal Server Error. If the server ever
   accepted the request and created a booking, the test saves the id so
   afterEach can delete it.

Expired token (bookingEdgeCases.spec.ts)
   Restful Booker tokens do not expire during a test run, so an expired token
   is imitated with a value the server never issued ('expired-token-0000').
   The server rejects it with 403. updateBookingWithRetry() then gets a new
   token and tries ONCE more. If a brand-new token is rejected too, it is a
   real login problem, and the test should fail - not loop.

Special characters (bookingEdgeCases.spec.ts)
   The name has Cyrillic letters, an apostrophe, & and #. In a web address &
   starts the next parameter and # starts a page anchor. Without
   encodeURIComponent the server would get a cut-off name, and the search
   would not find the booking. Date.now() makes the name unique.

Response time (bookingEdgeCases.spec.ts)
   Restful Booker is a free shared server, and its speed changes from run to
   run. The 5000 ms limit only catches "something is badly wrong", for
   example a request that hangs.

readBody() in helpers/bookingApi.ts
   Some Restful Booker errors are plain text ("Not Found", "Internal Server
   Error"), not JSON. readBody() tries to read JSON and, if that fails,
   returns the plain text. Without it the helper would crash, and the test
   would never reach its check.

Isolation (bookingIsolation.spec.ts)
   The test creates its own booking, checks it, deletes it and checks it is
   gone. It reads no data from other tests, so it gives the same result when
   run alone (npx playwright test bookingIsolation.spec.ts) or with the
   others in any order.
