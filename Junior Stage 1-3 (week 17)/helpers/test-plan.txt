Test plan - Week 17: Junior Stage 1-3
=====================================

Junior Stage 1 (first API call), Stage 2 (first real tests) and Stage 3
(structure, isolation, schema, AI).
API under test: Restful Booker - https://restful-booker.herokuapp.com

Start here. This file says what is in the project, which task is done where,
and where to find the evidence. The other files go into details.


In short
--------

- 16 tests in 6 files. All of them are green.
- 14 tests pass in the normal way.
- 2 tests are marked "expected to fail" (test.fail), because Restful Booker
  answers with a different status than the task asks:
  - creating a booking gives 200 instead of 201,
  - writing without a token gives 403 instead of 401.
- Every test that needs a booking creates its own and deletes it afterwards,
  so tests can run alone or in any order.
- CI on GitHub Actions: one green run and one red run were made and analysed.
- Why Restful Booker was chosen: docs/session-log.md in the repository root.

Words used in these files
-------------------------

test.fail
   A Playwright mark: "this test is expected to fail". If it fails, the run
   stays green. If it suddenly passes, the run turns red - a sign that the
   API has changed.

deviation
   A place where the API does not do what the task asks. The test still
   checks what the task asks, and is marked test.fail.

helper
   A normal function a test calls on purpose, for example createBooking().

fixture
   Something Playwright prepares before a test and hands to it. Here: a fresh
   login token ("authToken").

schema (zod)
   A description of what a correct answer looks like - every field and its
   type. One check against the schema proves the whole answer is right.

factory
   A function that makes new test data, for example buildBooking().

CI, pipeline, artifact
   CI runs the tests automatically on GitHub after every push. A pipeline is
   the list of steps it runs. An artifact is a file it keeps after the run,
   here the HTML report.


How to run
----------

In the folder "Junior Stage 1-3 (week 17)":

   npm ci                    install the packages
   npx tsc --noEmit          check the TypeScript types
   npx playwright test       run all tests
   npm run test:report       open the HTML report of the last run

More commands (one file, one test) are in project-files-explained.txt.
Settings: see ".env" in project-files-explained.txt. Without a .env file the
tests use the public Restful Booker address and its demo login.

Stage 1 - the first successful API call
=======================================

Test:    bookingSmoke.spec.ts - "GET /booking returns a list of booking ids"
Checks:  the status is 200, and the body is a list.
Shows:   prints the status and the first entries - the "view the response"
         part of the task.
Result:  passes, locally and in CI. This one test proves that the project,
         the packages and the test runner work end to end.


Stage 2 - the required practice tests
=====================================

1. GET a resource
   File:    bookingCrud.spec.ts
   Test:    GET /booking/{id} for a booking the test created.
   Checks:  status, first name, last name, total price, and the whole answer
            against the zod schema.
   Result:  200, passes.

2. POST with valid data
   File:    bookingCrud.spec.ts
   Checks:  status 201, the answer repeats the sent data, a booking id exists.
   Result:  Restful Booker answers 200, not 201. The test still checks 201 and
            is marked test.fail (assertion-notes.txt).

3. PUT, then check the change
   File:    bookingCrud.spec.ts
   Checks:  PUT with a valid token, the answer against the zod schema, then a
            GET shows the new value.
   Result:  200 on PUT, the GET shows the change. Passes.

4. DELETE, then check it is gone
   File:    bookingCrud.spec.ts
   Checks:  DELETE with a valid token, then GET the same id - must be 404.
   Result:  201 on DELETE (unusual, but that is this API), 404 on GET. Passes.

5. Wrong Content-Type
   File:    bookingCrud.spec.ts
   Checks:  the task says "observe", so the status and body are printed, and
            the test only checks that the server answered.
   Result:  500 Internal Server Error (plain text).

6. No Authorization
   File:    bookingAuth.spec.ts
   Checks:  PUT without a token must give 401.
   Result:  Restful Booker answers 403, not 401. Marked test.fail.


Techniques the task requires ("at least one test must...")
----------------------------------------------------------

Array.every()
   bookingCollection.spec.ts - every item in GET /booking has a numeric id.

Missing or null fields
   bookingCollection.spec.ts - a filter that matches nothing gives an empty
   list; body[0]?.bookingid gives "undefined" instead of a crash.
   bookingEdgeCases.spec.ts - the same for a nested field.

Strict equality (===)
   Inside the every() and some() callbacks. All equality checks use toBe,
   which is strict too. Loose == is never used.


Other Stage 2 topics (bookingEdgeCases.spec.ts)
-----------------------------------------------

Kept in a separate file, so the required tests above stay short.

Expired token and retry
   A PUT with a token the server never issued gets 403.
   updateBookingWithRetry() gets a new token and tries once more -> 200, and a
   GET confirms the change.

PATCH
   Only the last name is sent. A GET shows the last name changed, and the
   first name and total price stayed the same.

Nested JSON
   bookingdates.checkin is checked for type and value. A nested field that
   does not exist gives "undefined" instead of an error.

Special characters
   A name with Cyrillic letters, ', & and # comes back unchanged, and is found
   again with an encoded search (encodeURIComponent).

Response time
   GET /booking must answer in less than 5 seconds. A rough check, not a
   performance test.


Stage 3 - structure, isolation, schema, helpers
===============================================

Files by topic
   Smoke, Crud, Auth, Collection, EdgeCases, Isolation - all for bookings.

Setup and cleanup
   - "Booking CRUD", "Booking auth" and "Booking edge cases" create a new
     booking before each test (beforeEach) and delete it after it
     (afterEach).
   - "Booking creation" and "Booking input encoding" create the booking
     inside the test; afterEach deletes it.
   - bookingIsolation creates and deletes its booking inside the test.
   - The smoke, collection and response-time tests only read, and create
     nothing.
   No test uses data left by another test.

Configuration
   The API address and the login come from .env (BASE_URL, AUTH_USERNAME,
   AUTH_PASSWORD), read in playwright.config.ts and helpers/bookingApi.ts.
   Nothing is hardcoded in the test files.

Helpers
   helpers/bookingApi.ts (list in the project tree above). Tests call
   Playwright's request directly in two cases:
   - a broken request on purpose (no token, wrong Content-Type) - the helpers
     never send those;
   - a plain GET /booking in the smoke and response-time tests.

Schema check in at least 2 tests
   bookingSchema (models/booking.model.ts) checks the GET and the PUT answers
   in bookingCrud.spec.ts. The POST test has a schema check too, but it is not
   counted: that test is test.fail and stops at the 201 check before it.

Isolation proof
   bookingIsolation.spec.ts creates its own booking, checks it, deletes it
   and checks it is gone. Same result when run alone
   (npx playwright test bookingIsolation.spec.ts) or with the other tests.

AI-assisted work
   ai-prompt-template.txt - a reusable prompt for test ideas, and which ideas
   were accepted, rejected or changed.


Why this structure (Stage 3 evidence)
-------------------------------------

fixtures/ is separate from helpers/
   A fixture plugs into Playwright's "test" and is handed to a test
   automatically. A helper is a normal function a test calls on purpose. The
   import line shows which one a test uses.

models/ is separate from test-data/
   models/ says what a booking looks like (types and the schema that checks
   real answers). test-data/ says how to make one for a test. A test can check
   any answer against the schema, however the request was made.

Named status codes instead of numbers
   HttpStatus.NOT_FOUND says what is meant; a plain 404 makes the reader
   remember the code. It is a simple list, not a big abstraction.

One bookingApi.ts, not a file per HTTP method
   All functions work with the same resource and read answers the same way.
   Splitting them into get.ts, post.ts... would spread one topic over many
   files.

Configuration in .env, not in the code
   The same tests can run against another server or user by changing only
   the settings.
