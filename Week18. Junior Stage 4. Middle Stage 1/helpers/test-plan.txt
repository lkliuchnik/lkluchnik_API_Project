Test plan - Week 18

Junior Stage 4 (first realistic CRUD tests) and Middle Stage 1 (refactoring).
API under test: DummyJSON - https://dummyjson.com

Start here. This file says what is in the project, which task is done where,
and where to find the evidence. The other files go into details.

Words used in these files
-------------------------

test.fail
   A Playwright mark: "this test is expected to fail". If it fails, the run
   stays green. If it suddenly passes, the run turns red - a sign that the
   API has changed.

deviation
   A place where the API does not do what the task asks. The test still
   checks what the task asks, and is marked test.fail.

fixture
   Something Playwright prepares before a test and hands to it. Here: the
   ready-to-use services ("api") and a fresh login token ("authToken").

client, service, model
   The three code layers. The client sends HTTP requests. A service has one
   method for each endpoint of one resource (products, users...). A model is
   a TypeScript description of the data that is sent or received.

factory
   A function that makes new test data with sensible defaults, for example
   buildUser({ role: 'admin' }).

precondition
   A step that only prepares the test (for example "who am I?"). Its status is
   checked with a message that starts with "precondition:".

chain
   A test where the answer of one request is used in the next request.


How to run
----------

In the folder "Week18. Junior Stage 4. Middle Stage 1":

   npm ci                    install the packages
   npx tsc --noEmit          check the TypeScript types
   npx playwright test       run all tests
   npm run test:report       open the HTML report of the last run

Settings: an optional .env file in this folder (it is not in git):
   BASE_URL=https://dummyjson.com
   AUTH_USERNAME=emilys
   AUTH_PASSWORD=emilyspass
Without .env the tests use exactly these values - the public DummyJSON
address and the demo user from the DummyJSON docs.

CI runs the same steps on GitHub:
   .github/workflows/week18-junior4-middle1.yml (in the repository root)
It starts only when something in this folder or in that file changes.

Junior Stage 4 - the practice tasks
===================================

Task 1. A complete CRUD flow for one resource
   File:    productCrud.spec.ts
   Test:    "full CRUD flow: create, read, update, delete, verify absence"
            create -> read -> update -> delete -> check it is gone (404)
   Result:  test.fail - DummyJSON does not save the new product.
   Also:    "each CRUD step on an existing product returns the expected data"
            Read, update and delete on product 1. Passes. It shows what the
            API really answers at each step.

Task 2. Unauthorized access is rejected
   File:    auth.spec.ts
   Tests:   no token                  -> 401 + message, no data     passes
            random text as token      -> 401 + message              passes
            valid token               -> 200 + products             passes
            real token, forged end    -> 500 instead of 401         test.fail

Task 3. Pagination: number of pages, items per page
   File:    pagination.spec.ts
   Tests:   page 3: limit, skip, 10 items, enough products in total   passes
            last page has the rest, the page after it is empty        passes
            page 1 and page 2 share no product                        passes
   Note:    DummyJSON has no "page" field, so the test works it out:
            page = skip / limit + 1
            number of pages = total / limit, rounded up

Task 4. Create, change, and check that the change is saved
   File:    userData.spec.ts
   Test:    "create a user, change it, and the change persists"
   Result:  test.fail - DummyJSON does not save the new user.

Task 5. A duplicate is rejected
   File:    userData.spec.ts
   Test:    "creating a user with an existing username and email fails"
            The username and email are taken from a real user (GET /users/1).
            The test expects 409 Conflict.
   Result:  test.fail - DummyJSON creates the duplicate (201).


What the task wants to see
--------------------------

Requests that use data from earlier answers
   Eight chains, explained in chaining-explained.txt.

Business results, not only "200 OK"
   Cart totals, carts that belong to me, catalog prices, an update that
   changes only what was sent, page rules, clear error messages.
   See "Business rules" in assertion-notes.txt.

Tests that show what the system really does
   The 5 test.fail tests show real problems of the API instead of hiding them.


Optional topics, also covered
-----------------------------

User A and user B
   auth.spec.ts - user A can read user B's carts (test.fail).
Validation errors
   auth.spec.ts - wrong password, missing password (400 + message).
   carts.spec.ts - a cart for a user that does not exist (404 + message).
Response time
   pagination.spec.ts - a page of products in less than 3000 ms.

Middle Stage 1 - the practice tasks
===================================

Task 1. Review the Junior tests and find duplication
   ai-review.txt - round 1, findings D1-D10.

Task 2. A typed API client class with auth, base URL and error handling
   api/ApiClient.ts
   Base URL:  comes from playwright.config.ts; a "/" at the end is allowed.
   Auth:      "Authorization: Bearer <token>" is added when a token is given.
   Errors:    no answer from the server -> a clear error with method and path.
              An answer that is not JSON -> no error; the text is kept, so the
              test still sees the real status.

Task 3. TypeScript interfaces for at least 2 resources
   models/ - Product, User, Cart, login answer.
   Also what we send: NewProduct, NewUser, NewCartItem.
   Shared: ApiResponse<T> (status + body) and Page (total, skip, limit).

Task 4. A factory function with defaults
   test-data/userFactory.ts - buildUser({ role: 'admin' })
   Every field has a default; a test passes only what it cares about.
   Used in userData.spec.ts: "a new user created as admin gets the admin role".
   Same idea: buildProduct() in productFactory.ts.

Task 5. Refactor at least 3 tests to the new layers
   All 20 Junior tests in all 6 files. The old helper file is deleted.

Task 6. Explain the before/after improvement
   refactoring-decisions.txt.

Task 7. AI finds duplication and suggests refactoring
   ai-review.txt (round 1) and refactoring-decisions.txt.

Task 8. AI reviews the tests for maintainability; selected fixes applied
   ai-review.txt (round 2). Two more AI reviews checked the NEW code after the
   refactoring (rounds 3 and 4).
