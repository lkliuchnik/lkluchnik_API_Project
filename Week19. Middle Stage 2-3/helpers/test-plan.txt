Words used in these files
-------------------------

client (ApiClient)
   The one class that sends HTTP requests. Every answer comes back in the
   same shape: status, ok, body, durationMs, attempts.

interceptor
   A small function every request passes through on its way to the server.
   Here: auth (adds the login token), retry (tries again when the server is
   briefly down), logging (writes each request to the report).

service
   A class for one resource, with one method per endpoint - for example
   api.posts.getByUser(1) sends GET /posts/user/1.

fixture
   Something Playwright prepares before a test and hands to it - for example
   "authApi", the services with a logged-in client.

environment
   A named set of settings (test user, retries, timeout). Chosen with
   TEST_ENV=dev or TEST_ENV=staging; the code stays the same.

seeded data
   Test data that is ready before the test starts. DummyJSON does not save
   new data, so there it is existing data found through the API. DemoQA
   does save data, so there each test gets a new account of its own.

test.fail
   A Playwright mark: "this test is expected to fail", because the API does
   not do what the task asks. If it ever passes, the run turns red.

matrix (CI)
   One CI workflow that runs the same job several times with different
   settings - here once for dev and once for staging.

API + UI test
   A test that prepares data through the API and then checks the web page
   in a real browser. Tagged @ui.

coverage gap
   A risk that no test checks yet.

S1 ... S10
   The 10 test ideas the AI drafted for the Book Store (ai-review.txt,
   task 1). The same numbers are used in coverage-gaps.txt and here.

token
   A long text the server gives after a login. Requests send it to prove
   who they are. DemoQA keeps only the newest token of an account.

ISBN
   The number that identifies a book, for example 9781449325862. The Book
   Store uses it as the book's id.

precondition
   A step that only prepares a test (open an account, read the catalog).
   Its check says "precondition:", so a broken setup is easy to tell apart
   from a real failure.

Middle Stage 2 - the practice tasks
===================================

Task 1. A base API client class
--------------------------------

The task: a client that handles auth, headers, base URL and response parsing.

Where:   api/ApiClient.ts, api/createApiClient.ts, api/interceptors/

Base URL
   Each API has its own, from config/environments.ts. A "/" at the end of
   the address is fine.

Headers
   Every client sends JSON headers (set in createApiClient). A request can
   add its own headers. A token becomes "Authorization: Bearer <token>".
   The headers are not in playwright.config.ts, so they will not reach the
   browser pages of the UI tests in Stage 3.

Response parsing
   Always the same shape: status, ok, body, durationMs, attempts. An answer
   that is not JSON is kept as text. A 4xx or 5xx answer is returned, not
   thrown - negative tests need to see it.

Auth interceptor - checked by 4 tests in tests/dummyjson/interceptors.spec.ts
   - it adds the token, so GET /auth/me works without passing one;
   - a rejected token is refreshed once, and the request is sent again;
   - if no new token can be got, the test gets the 401, not an exception;
   - a token passed by the test is left alone, even a wrong one.

Retry interceptor - checked by 5 tests in the same file
   - a GET that keeps getting 503 is sent 3 times, then the 503 is returned;
   - a GET that gets 500 is not sent again (a server bug answers the same);
   - a POST that gets 503 is not sent again (it could create data twice);
   - a GET with no answer at all is tried 3 times, then the error is thrown;
   - a GET that succeeds is sent once.

Logging interceptor - checked by 1 test in the same file
   - one line per real request: method, path with query, status, time.
     The lines are attached to every test's HTML report as "api-log".

What changed compared to the week 18 code
-----------------------------------------

- Every layer now has one folder per API: services/dummyjson,
  models/dummyjson, tests/dummyjson, test-data/dummyjson,
  assertions/dummyjson. The fixture file is fixtures/dummyjson.fixture.ts.
- The test user comes from the environment, not from a fixed file.
- The client got interceptors, headers per client and per request, and three
  more fields in the answer (ok, durationMs, attempts).
- AuthService can refresh a token. Services that need a login take the token
  as optional - authApi adds it by itself.
- playwright.config.ts has no address and no headers any more; it shows the
  environment name in the HTML report.
- The response-time test reads the time from the answer, and checks that no
  retry is hidden inside it.
- All other week 18 tests check the same things as before.

Task 1. A 4+ step API flow across related resources
---------------------------------------------------

Where:   tests/bookstore/readerJourney.spec.ts - one test, 9 steps
Flow:    open an account -> log in (token, authorized) -> add two catalog
         books -> the account shows them with the catalog details -> replace
         one with a third -> delete one -> only the third is left -> close
         the account -> the closed account can neither log in nor be read
Related resources: account, token, catalog, collection. Every step uses data
from the steps before it (user id, token, ISBNs, catalog details).

Task 5. A business rule beyond simple field validation
------------------------------------------------------

Where:   tests/bookstore/businessRules.spec.ts and collection.spec.ts
   - a book can be in a collection only once - and the same rule must hold
     when a book is REPLACED (it does not: test.fail, a defect);
   - a collection belongs to its owner: another reader can neither read,
     change, empty nor close it;
   - a request either works completely or changes nothing (it does not:
     test.fail, a defect);
   - the books in a collection have exactly the catalog details
     (readerJourney.spec.ts, step 4).

Code review before the commit
-----------------------------

Two AI reviewers read the new code separately: one looked for bugs, one for
the architecture. Every finding was checked in the code before a decision.

Fixed
   - A test passed a whole reader (with its session and token) where only
     the user name and password were needed, and all of it went into the
     request body. AccountService now sends only the user name and password.
   - The owner test checked "another reader gets 401" but not "and nothing
     changed". It now also checks that the owner's collection is empty.
   - The journey test registered its account for cleanup only after two
     more checks; if one failed, the account was left on the server. It now
     registers it right after the account is created.
   - Unused code removed: BookStoreService.getBook() and model fields no
     test needs.
   - A failed DemoQA login now shows the HTTP status in the error message.
   - The comments above the 3 Book Store test.fail tests point to
     assertion-notes.txt, like the DummyJSON ones.

Not changed, on purpose
   - "A test.fail test also counts a broken setup step as the expected
     failure" - a known limit, described in assertion-notes.txt (Limit).
   - Two possible token races (two logins in the same second, two refreshes
     at the same time) - nothing in the tests triggers them today.
   - The fixture names readerApi and bookstore stay: readerApi is logged in
     as one reader, not as the environment's user like authApi.
   - The two "a new account is rejected" tests (weak password, taken name)
     do not register an account for cleanup: none is created. If DemoQA ever
     accepted one, the test would turn red and that account would stay on
     the demo site.
   - A Book Store GET in staging can wait longer than the test timeout when
     DemoQA is down (README.txt, part 4).
